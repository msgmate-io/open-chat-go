Private documentation for the `tui` integration: a full-screen terminal client
that runs in-process in the `open-chat` binary when the integration is part of
the build. It connects to one or more Open Chat servers, keeps you signed in on
the device, and lets you chat with your default bot — or attach to an existing
chat — without leaving the shell.

How the TUI is embedded, forwarded and provisioned — including the integration's
own deployment assets — is documented in the integration's own docs, which you
can open from the [Integrations & Tools](/docs#integrations) overview.

## Launching

```bash
open-chat tui
```

The TUI runs directly from the `open-chat tui` subcommand (no separate binary is
downloaded, extracted or looked up on `PATH`). If your build omits the `tui`
integration, the subcommand is not registered.

## Using it

The UI is modal and vim-first: `NORMAL` is the default and the composer (and the
auth/form fields) use `INSERT`. A tabline, a reverse-video statusline (mode,
session/model, scroll ruler) and a command line frame every view. The cursor is a
blinking block in `NORMAL` and a blinking bar in `INSERT`.

- Move with the arrow keys or `j`/`k`, confirm with `Enter`.
- **Servers** — add, edit, delete and switch between Open Chat servers. A local
  server (`http://127.0.0.1:1984`) is available by default.
- **Sign in** — either through **Browser Login**, which opens the Open Chat CLI
  authorization page and polls until the device is approved, or by pasting a
  personal access token (`ocat_…`) under **Authorize via API key**.
- **Pick a model** — a new chat with the default bot first asks which of the
  bot's models to use (the last choice is preselected and remembered). The
  choice is sent as the chat's `shared_config`, so the server routes the reply to
  that model's provider.
- **Chat** — the chat starts as a `conversation` with the default bot; press
  `i` to compose and `Enter` to send. The composer supports vim motions
  (`w`/`b`/`e`, `0`/`$`, `x`/`D`/`C`/`s`, `A`/`I`). `:`, `/`, `?` and `\` open the
  command palette, search, help and which-key panels. When a chat is pre-bound
  (see below) the TUI attaches to it directly instead of creating a new one.
- **Pick a chat** — `p` lists your conversations and interactions (including
  chats created in the web UI) and attaches to the selected one.

### Catalog commands

The palette (`:`) exposes three read-only catalogs, so the pickers work without
any wider credential than the token the client already holds:

| Command | Route | Behaviour |
| --- | --- | --- |
| `:models` | `GET /api/v1/models` | pick the model used for the next turn (sent as the chat's `shared_config`) |
| `:tools` | `GET /api/v1/tools` | inspect the tool catalog, including whether a tool needs init or confirmation |
| `:bots` | `GET /api/v1/bots/list` | list the bots you may use and switch this interaction to the picked one; v1 stops at bots the acting user already owns or may read |
| `:sessions` | owner session list | scroll the sessions you still own and attach the picked one back into this view; destroyed, expired and duplicate rows for one chat are hidden |

`:models`, `:tools` and `:bots` are plain catalog reads: they cannot mutate
remote state, and the sibling write routes (`POST /models`, `PATCH
/bots/{identifier}`, `PUT /bots/{identifier}/config`, `POST /bots/list`) stay
denied. `:bots` v1 deliberately stops at bots the caller already knows;
discovering bots nobody interacted with yet is left to the web UI. `:sessions`
reads the owner-scoped session list and only pre-selects a row: re-attaching the
chosen session stays an explicit action.

### Keys

| Key | Action |
| --- | --- |
| `h j k l` / arrows | move (`3j` counts); in the composer `h`/`l` move the caret |
| `w` / `b` / `e` | composer word motions (`NORMAL`) |
| `gg` / `G` | top / bottom |
| `Ctrl-d` / `Ctrl-u` | half page down / up |
| `i` `a` `A` `I` | enter `INSERT` (before / after / line end / line start) |
| `x` `D` `C` `s` | composer delete / change (`NORMAL`) |
| `Enter` | open / select / send |
| `Esc`, `Esc Esc` | stop a live turn, otherwise leave `INSERT` then go back |
| `/` `:` `?` `\` | search, command palette, help, which-key |
| `q` | close view / quit |

## Status and control

While a turn is running the TUI renders a compact status footer driven by
`GET /api/v1/chats/{chat_uuid}/status` (the same response the web integration
consumes): `is_active`, `state`, `latest_message_finished`, optional
auto-continuation (`auto_continue`, `auto_continue_turns` / `auto_continue_max`,
`auto_continue_stop_reason`), `stalled` (with `stall_reason`,
`stall_age_seconds`, `stall_threshold_seconds`), `queued_replies` and
`auto_continue_incomplete_retries`.

- **Poll cadence** — poll `/status` about every 2s *while `is_active`* and stop
  as soon as the turn finishes; there is no need to poll an idle chat.
- **Follow the stream** — `GET /api/v1/chats/{chat_uuid}/messages/streaming`
  returns the in-flight assistant snapshot (with a `seq`). Poll it at a faster
  cadence (~500ms) to render output that arrives between message polls, then
  let the authoritative message from `messages/list` replace the snapshot once
  the turn lands.
- **Stop a turn** — press `Esc` (or `Ctrl-C`) to `POST
  /api/v1/chats/{chat_uuid}/signals/interrupt`. The interrupt cancels the live
  bot-reply task, drops the replies queued behind it, and asks a detached chat
  backend (for example an external coding agent) to abort its generation; work
  the stopped turn already persisted is preserved.
- **Queue instead of interrupting** — sending a message while a turn is live is
  queued by default (`delivery_mode: "queued"`, surfaced as `queued_replies`);
  `delivery_mode: "interrupt"` stops the live turn and starts the new one
  immediately, which is what a "send now" affordance uses.

### Live fine grained stream

The 2s `/status` poll and the ~500ms snapshot poll are backstops. The live path
is the authenticated interaction websocket
(`/api/v1/interaction/messages/ws`) opened with `?stream=fine`. Without that
query parameter the socket only carries the coarse legacy frames, so the TUI
would show a turn as "running" while the assistant silently calls tools.

With `stream=fine` the socket carries small frames that each name one thing that
changed, and the TUI applies one frame to one row - it never re-renders the
transcript array:

- `tool_call_started` / `tool_call_updated` / `tool_call_ended` - a tool call row
  keyed by `tool_call_id`, appended once and then updated in place, so the user
  watches `coder_read`, `coder_bash`, ... start, change status and finish as it
  happens.
- `status_changed` - the footer state (`state`, `is_active`, stall and queue
  counters) without polling `/status`.
- `reasoning_delta` - appends to the reasoning row; `partial_snapshot`
  reconciles the assistant text and the reasoning with the accumulated turn text.
- `new_partial_message` and the legacy message frames stay accepted, so a turn
  replayed from a legacy socket renders identically.

Frames for another `chat_uuid` and frame types the client does not know yet are
dropped rather than treated as errors, so a server that grows new events does not
break an older client mid-turn. A cancelled turn (Esc) closes the socket without
surfacing a stream error.

## Configuration

Servers and tokens are stored in a device-scoped JSON file under the platform's
user config directory (for example
`~/.config/open-chat-go/tui/config.json` on Linux). Tokens are written with
`0600` permissions on Unix, so the device stays authorized until the token
expires. Override the location with `OPEN_CHAT_TUI_CONFIG_DIR`.

Several `open-chat tui` sessions may run side by side on one device. A session
that an integrating deployment starts for you gets its own private directory
inside the config dir instead of the shared file, so two shells never write the
same file nor clobber the other's active server and chat selection; log in once
per directory, or point `OPEN_CHAT_TUI_CONFIG_DIR` at a directory of your own to
share one. How those per-session directories are provisioned belongs to the
integration's own docs.

```json
{
  "servers": [
    { "name": "msgmate.io", "url": "https://msgmate.io", "token": "…" },
    { "name": "local", "url": "http://127.0.0.1:1984" }
  ],
  "active": "msgmate.io",
  "default_bot": "bot"
}
```

Useful flags:

```bash
open-chat tui --bot coder-bot  # open a chat with a specific bot
open-chat tui --where          # print the config file path
open-chat tui --version
```

### Environment overrides

The TUI also honours environment variables, so a scripted login can start it
without an interactive prompt:

- `OPENCHAT_SERVER_URL` — server to dial back to (overrides the active server's
  URL).
- `OPENCHAT_ACCESS_TOKEN` — bearer token to use without an interactive login
  (an integrating deployment may also inject a namespaced alias of the same
  variables; see its integration docs).
- `OPENCHAT_CHAT_UUID` — attach to this existing chat instead of creating a new
  one.
- `OPEN_CHAT_TUI_CONFIG_DIR` — directory holding the generated `config.json`.

The TUI talks to the regular HTTP API (version probe, `user/self`, the CLI
browser-auth endpoints, chats and messages), so anything that works in a browser
session works from the terminal too.
